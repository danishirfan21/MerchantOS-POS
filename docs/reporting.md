# Historical reporting contracts

GET `/api/admin/reports/orders` and `/api/admin/reports/orders.csv` require the new explicit HistoricalReporting Administrator policy. Existing /api/orders and Cashier-owned receipts are unchanged. GET `/api/admin/reports/sales` combines summary, trend, payment breakdown and top 10 products from one PostgreSQL repeatable-read, read-only snapshot; reports never modify business data.

Orders: page defaults1, max10,0000; pageSize defaults20, max100. Ordering is created_at DESC,id DESC. SQL filters/count/pagination never load all receipts. Offset pagination preserves existing numbered navigation, but deep offsets cost more and new concurrent inserts can shift pages between requests; this is not an immutable cross-request snapshot. Counts and rows within one response share a snapshot.

Date selections use Asia/Riyadh, independent of host/browser timezone. `range=today|yesterday|week|month|custom` means Today, Yesterday, Last7Days including today, Last30Days including today, or custom dates. Custom `from`/`to` are ISO yyyy-MM-dd store dates, both inclusive in the UI/API; SQL converts to UTC [start midnight,end+1 midnight). Maximum366days; future selected days are rejected. Empty past periods are valid zero-sales reports. Orders/export additionally allow range=all (default) for complete history. Sales defaults today. Only custom accepts from/to; malformed, reversed, future, oversized or unknown filters return400.

Orders/export accept search (literal case-insensitive order-number substring, max120), paymentMethod cash/card, status completed/cancelled/failed, and date filters. Orders response includes items, page/pageSize, total matching count, hasMore and normalized filter. Exports ignore pagination (page/pageSize are rejected) and use exactly the same WHERE conditions; maximum10,000matching rows, otherwise413 before any CSV is returned. UTF-8 BOM, quoted RFC-style cells, doubled quotes/newlines and formula-prefix protection on every cell; safe fixed filename and no credentials/internal actor IDs.

Summary counts only completed SAR orders. Gross=subtotal (before discount, before VAT); discounts=discount snapshots; netBeforeVat=gross-discounts; vat=VAT snapshot; revenue=final payable (includes VAT); AOV=revenue/completedCount rounded half-up to integer halalas (zero for no sales). No join to items/payments in order-level sums. Payment breakdown uses order.payment_method snapshots, cash/card amounts/counts and decimal revenue shares; card means simulated card, not settlement. Top products sum quantity*unit_price snapshots, before discount/VAT, grouped by product ID, with the latest sale's historical name; never current product prices.

Single-day reports return24zero-filled local-hour buckets; ranges2–31days return daily buckets; longer ranges return month buckets. Buckets are clipped to the selected interval, not interpolated. Values are completed tax-inclusive SAR revenue and order counts. All money stays integer halalas; percentage display uses decimal arithmetic.

Migration006 adds chronological, completed-SAR covering and order-item lookup indexes without changing data. Commands time out after10seconds; CSV memory is bounded to10001short order summaries. Leading-wildcard substring search can require scanning the selected order window; no trigram extension is introduced. Aggregation is SQL-side but historical scans are still proportional to the chosen period. CI verifies a10,000order isolated fixture and EXPLAIN; no production-scale latency guarantee is inferred.
