# Monitoring, alerts and escalation

The collector uses public readiness endpoints, a dedicated aggregate-only `merchant_monitor` PostgreSQL view and a separately mounted random monitor token for sanitized POS/Admin metrics. The token authorizes only `/api/ops/monitor` or `/ops/monitor`; it cannot authorize business routes, users, MFA or operator commands. Existing Administrator-only metrics remain protected. Do not expose collector configuration/credentials or textfile state through public ingress.

A private monitor JSON requires: posReadiness, adminReadiness, posMetrics, adminMetrics, caBundle, monitorTokenFile, databaseConfiguration (`{"dsn":"..."}` in a separate 0600 file), backupStateDirectory, storageConfiguration, capacityPath, certificates (tls/dp/backup public certificate paths), metricsState, prometheusTextfile, auditVerificationFile, restoreVerificationFile, securityPolicy, releaseGate, rules, alertState, alertReceiver, alertCaBundle and alertTokenFile. All transport URLs require TLS; receivers are independently configured, never inferred from a connected communication account.

Run `python deploy/operations/monitor.py --config /run/secrets/monitor.json`, normally using the provided systemd service/timer every 30 seconds. Prometheus-compatible numeric textfile output can be consumed by an existing trusted node/textfile collector. JSON state records observation time and delivery backlog. This is a small collector/rule engine, not a new Admin dashboard or an HA observability platform.

`alert-rules.json` defines severity, threshold, evaluation duration and runbook reference. Availability needs a sustained 30–60 seconds, backup failure/recovery/certificate events are immediate where appropriate, disk pressure needs 120 seconds, and MFA failure thresholds aggregate five minutes. HTTP 5xx and unexpected checkout 5xx use sampled cumulative-counter deltas; normal 401s and inventory conflicts do not page. Reporting latency is bounded to the last five minutes/1,000 samples. Process metrics reset on restart; negative deltas are treated as resets.

| Alerts | Immediate action / responsible role |
|---|---|
| PosUnavailable, AdminUnavailable, PosMetricsUnavailable, AdminMetricsUnavailable | Service operator: correlate readiness with last change, resource limits and TLS trust; avoid login/recovery bypasses |
| DatabaseUnavailable, PosHttpErrors, AdminHttpErrors, CheckoutErrors | Database/service operator: restore availability; keep the original checkout/stock idempotency key when results are uncertain; never retry with a new key |
| BackupFailed, BackupOverdue | Backup operator: inspect safe failure category/private config, storage reachability, certificate validity, temp capacity and last verified receipt; bounded retry, no deletion of unuploaded data |
| AuditBacklog, AuditSignalsUnavailable | Audit operator: inspect pending/oldest age and destination, resume exporter; do not delete pending events or weaken local transaction guarantees |
| AuditIntegrityFailed, AuditVerificationOverdue | Security responder + witness custodian: preserve objects/checkpoint, stop trusting new checkpoints, compare independent anchor/versions; investigate before recovery |
| PrivilegedSecurityEvent, RepeatedMfaFailures, AuthenticationFailures, AccountLockouts | Security responder: verify approved case/maintenance, revoke compromised sessions, preserve events; independent person verification before recovery/reset |
| TlsCertificateExpiry, KeyCertificateExpiry, BackupCertificateExpiry | Certificate/key custodian: renew through controlled mounts, preserve old DP/backup recovery dependencies, exercise old/new verification |
| StorageUnavailable, StorageCapacity | Storage operator: validate endpoint/retention and capacity; expand approved capacity rather than discarding unverified backups/audit |
| ReleaseVulnerability, SecurityExceptionExpiry | Vulnerability reviewer: inspect exact-image findings, fix/rebuild/retest; expired exceptions block the gate; never auto-extend or suppress |
| RestoreVerificationFailed, RestoreVerificationOverdue | Recovery operator: schedule an approved isolated restore, validate hashes/quarantine/keys; no destructive automatic repair |

Export/readiness workers record errors by category without exception bodies, secrets or business data. A real receiver gets only schema version, alert name, severity, firing/resolved state, episode timestamp, observation value, runbook reference, delivery sequence and stable delivery ID. Receiver must authenticate the separate bearer token and deduplicate delivery IDs. The local fixture does both. Durable queue replay preserves delivery sequence across restart; failures remain pending and visible. Live operator routing is **unverified** until the owner configures a receiver, staffs escalation and confirms a test notification and resolution.

Run independent `audit.py verify --storage ... --checkpoint ... --certificate ... --status-file /trusted/audit-verification.json` on the witness/verification host. Mount its aggregate status read-only to monitoring; stale/missing/failed verification alerts. Retain the underlying signed checkpoint independently. A writable local status file alone is not a trust anchor.

Operational CI injects S3/receiver outages and supplies controlled alert values to verify every minimum rule's firing/resolution and durable retries. The HTTPS drill additionally polls the actual POS/Admin readiness and real PostgreSQL during a stopped-database scenario and delivers/resolves DatabaseUnavailable at the isolated TLS receiver. It sends no real emails, pages or chat messages. Expected recovery exercises should be announced/approved through the real operating procedure; no approvals or recipients are invented by the application.
